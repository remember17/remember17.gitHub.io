Meta 如何改造“全能 Agent”：1300 行薄编排器与 14 个专家的分工

Meta 的全能 Agent 在生产中出现幻觉，不同领域的知识相互干扰。团队改用约 1300 行的确定性编排器与 14 个上下文隔离的专家 Agent。本文介绍它们如何分工、怎样验证结果，以及小团队采用这套思路时需要考虑的取舍。

Meta 最近在工程博客里分享了一次 Agent 改造经历：团队原先做了一个「什么都懂」的 Agent，演示时运行正常，进入生产环境后却开始产生幻觉。

最终解决问题的办法，是缩小中间层的职责：让它负责分派任务，把具体工作交给各领域的专家，而不只是调整提示词或扩大上下文窗口。

10 月 19 日，Meta 工程师 Plawan Rath、Akhil Jindal、Ashwini Verma 介绍了这套「薄编排器」（Thin Orchestrator）架构。下面从原方案的问题讲起，看看新的分工如何运作、有什么限制，以及小团队可以怎样采用。

一、问题：给的知识越多，结果越差

Meta 要自动化的场景是：在推荐系统里接入一个新的数据字段。

这个任务需要横跨 3 个代码仓库、3 种编程语言，最多经过 6 个必须保持同步的管线阶段。管线采用「配置即代码」的方式：Python 配置驱动 C++ 代码生成，生成的代码交给数据处理服务，再由处理服务写入分析系统。

第一版方案把这些知识都交给同一个 Agent：领域知识、配置 schema、代码生成规则、管线路由逻辑、校验要求，以及 10 多个数据源各自的填充模式。

原文这样描述：「这个 Agent 拥有它需要的一切。问题就出在这里。」

上下文超过某个阈值后，继续增加知识反而降低了表现。不同领域的知识开始相互干扰：Agent 会把一个子系统的字段命名规则用到另一个子系统，或者在从 B 数据源取数时，套用 A 数据源的代码生成模式。

团队还尝试过另一种单 Agent 方案。工程师为每个任务手写定制系统提示时，成功率为 70–80%；没有这些定制提示，成功率就降到 10–20%。

Meta 因此认为，问题出在架构，不能只靠提示工程解决。

二、新架构：编排器分派任务，专家处理领域问题

整个系统被拆成两层。

第一层：确定性编排器

编排器大约有 1300 行代码，负责路由 20 多个工作流。它只做几件事：识别意图、收集必填字段、执行可靠性检查，再把任务交给对应的专家。

按原文的描述，它不分析代码、不生成配置，也不操作代码库。它的作用就是路由。

第二层：14 个专家 Agent

每个专家专注于一个领域，使用独立的上下文。

  • Schema 管理 Agent 负责配置注册表。
  • 填充 Agent 掌握为 10 个数据源分别生成代码的方法。
  • 校验 Agent 负责构建系统和质量检查。

没有任何一个 Agent 能看到全貌。这是团队有意设置的限制，用来保持各个专家的职责和上下文边界。

每个请求都走同一套 7 步协议

  1. 读取对应专家的说明文件
  2. 检查目标是否已经存在，防止重复
  3. 向用户收集必填字段
  4. 自动发现能推断出来的信息，比如仓库类型、现有配置
  5. 执行可靠性检查：确认是否有生效中的警告，或是否需要特定人员审核
  6. 把任务连同完整上下文交给专家
  7. 处理结果、明确报告错误、确认是否成功

这套协议把大模型的参与范围限制得很清楚：第 1–5 步和第 7 步都由确定性流程执行，只有第 6 步用到大模型，并且只加载本领域的知识，使用隔离的上下文。

图 2：7 步协议里只有第 6 步用到大模型；三个工作流模板复用同一组专家。由作者根据原文绘制。来源：Meta Engineering《The Thin Orchestrator》，发布于 2026 年 10 月 19 日。

三、加新能力时写模板，不写新 Agent

在我看来，这套设计最值得借鉴的是把「要做什么」和「每一步怎么做」分开。

工作流模板定义「要做什么」，专家负责具体执行。原文把模板称为「确定性状态机」，用来限制大模型可以作出的决策，举了三个例子：

  • 字段接入：Schema → 校验 → 填充 → 测试
  • 事件接入：Schema → 填充 → 校验 → 测试 → 事件处理
  • 管线迁移：评估 → 规划 → 填充 → 校验 → 监控

三个模板复用的是同一组 14 个专家，只是顺序不同。

管线迁移是一个新场景，但 Meta 只需编写新模板，重新安排现有专家的执行顺序。按原文的说法，这让团队在没有新增 Agent 代码的情况下，获得了完整的生产能力。

每个专家的结构都一样，包括 5 个部分：

  • 知识来源：运行时加载哪些领域文件，每个通常几千 token
  • 预收集清单：分派前编排器必须先收集哪些信息
  • 分步工作流：这个领域具体怎么执行
  • 发现模式：怎么在 monorepo 里找到相关代码
  • 故障排查：常见错误对应的解决办法

新增专家时可以沿用这一结构，不必从头设计。原文说，第 15 个专家和第 1 个在结构上一模一样。

领域知识也独立于编排器。团队维护着 25 个以上的知识文件，由专家在执行时按需加载。文件更新后，下一次会话就会使用新版本，无需修改编排器。

四、效果

Meta 自述的生产效果

Meta 在工程文章中给出了两组数字。它们都来自团队自述，我尚未找到独立复现；文章也没有交代统计涉及多少个字段或改动，以及统计的时间范围。

  • 新字段的配置准备时间：纯手工要 3–4 天，他们之前的配置驱动系统要大约 1 天，薄编排器系统不到 1 小时。
  • 改动质量：原文的说法是，约三分之二的改动落地时”没有经过大的人工修改”（without significant human edits）。

理解这些数字时，需要留意比较范围。准备时间对比的是 Meta 自己的两种旧做法——纯手工和此前的配置驱动系统；文章没有将它与其他 Agent 方案比较。改动质量则没有对照基线，也没有说明如何界定「大的人工修改」。

「三分之二无需大改」也不等于「只有三分之一需要人改」。这些改动仍可能经过小的人工修改；对于剩下的三分之一，原文没有交代修改比例或幅度。人工参与仍然是流程的一部分。

Meta 将这种取舍概括为「用通用性换领域深度」：编排器保持通用，专家则专注于各自的领域。

外部研究提供的参照

Meta 引用了西奈山医学院的一项研究，并称其为预印本；这篇论文的全文已于 2026 年 3 月 9 日发表在 npj Health Systems。

论文测试了 4 个模型：GPT-4.1-mini、GPT-4.1-nano、Llama-2-70B、Qwen-3-8B。合并 4 个模型的结果后，任务批量达到 80 个时，编排式多 Agent 的准确率为 65.3%，单 Agent 为 16.6%。

「token 最多相差 65 倍」则只来自 GPT-4.1-mini：处理 80 个任务时，多 Agent 用了约 6 万 token，单 Agent 用了约 390 万。两个开源模型在单 Agent 大批量运行中有不少直接失败的情况，论文指出，这影响了 token 对比的可比性。

这项研究的场景与 Meta 不同。它使用受控的检索、抽取和剂量计算任务，每题都有确定的标准答案，按精确匹配评分，并未测试代码生成或跨仓库工程任务。论文作者也指出，还需要在真实病历和临床流程中验证。它为「任务隔离可以减少上下文干扰」提供了参考，但结果不能直接套用到其他产品。

五、为什么有效

Meta 认为，新架构让各组件的职责边界与计算边界对齐，主要体现在以下四点。

这些解释针对的是 Meta 自己的实现，前提是专家之间确实隔离了上下文，编排器也确实不依赖大模型路由。文章没有提供对应的测量数据，因此不能把它们视为这类架构普遍具备的保证。

1. 用确定性代码处理确定性决策。 在这套系统中，「把任务交给哪个专家」可以由路由规则决定，无需让大模型推理。

2. 隔离上下文，减少知识干扰。 负责 A 数据源的填充 Agent 看不到 B 数据源的模式。原文称「它没法幻觉出错误的那一个」（It can’t hallucinate the wrong one）。

我的理解是，隔离有助于降低「把 B 的模式套到 A 上」这类跨数据源干扰的风险，但不能消除错误。如果专家的知识文件有误，或编排器分派错了任务，系统仍会出错；专家在自己的领域内也可能犯错。

3. 隔离故障影响。 按 Meta 的描述，专家执行失败时，编排器会重试或上报，失败不会污染编排器的状态或其他专家的上下文。

我的理解是，这需要具体实现来保证，例如专家之间不共享上下文，结果先交回编排器，再进入下一步。原文没有提供故障率或隔离失效的数据。

4. 各层可以分别改进。 Meta 的说法是，更好的模型会让 14 个专家同时改善，更新知识文件即可生效，新增模板也无需修改 Agent 就能扩展能力。

这是对架构的描述。文章没有提供更换模型前后的对比数据，各个专家的表现也未必会随模型更换而同步提升。

在我看来，原文对重编排器风险的说明更有说服力：一旦编排器产生幻觉，错误就会传到下游，例如把任务交给错误的 Agent、收集错误的字段，或跳过可靠性检查。

薄编排器的路由和检查不依赖大模型推理，因此减少了这一环节产生幻觉的空间。不过，关键词和规则写错仍然会造成错误路由，只是这类问题更容易复现和排查。

维度重编排器 / 全知单体 Agent薄编排器 + 专家 Agent
路由谁来做LLM 推理决定交给谁、怎么做确定性代码：关键词、意图分类、字段收集
上下文所有知识塞进一个上下文每个专家只加载自己的知识文件
出错时错误向下游扩散：错路由、错字段、跳过检查按 Meta 自述：失败被隔离，编排器重试或上报
适配新任务文中另一单 Agent 方案：每个任务人工定制系统提示先问能否用新模板复用现有专家
更新知识知识写进编排器，改知识就要动编排器（作者归纳）运行时按需加载，下次会话即用新版，编排器不用改
代价（作者归纳）通用、上手快牺牲通用性换领域深度；要维护模板和知识文件

六、把验证纳入固定流程

在《AI 写的代码越来越多，软件岗位招聘却在回升》中，我讨论过一个变化：AI 写代码之后，瓶颈逐渐从编写转向验证。Addy Osmani 10 月 14 日在 Substack 发表的《Agentic Verification》也谈到这一点，副标题是：「瓶颈已经从写代码，变成了知道代码是对的。」

他的主要观点可以概括为：

  • 如果 Agent 没法验证自己的输出，它本质上就是在猜。
  • 我们的工作，不再是逐行审代码，而是搭建 Agent 自己能跑的验证循环。
  • 他宁可要一个好得多的反馈循环，也不要一个稍好一点的模型。
  • 测试必须快且确定。否则 Agent 会学会”重跑一遍”，而不是修问题。
  • 用独立上下文的评审 Agent 来做验证；生成的测试本身也要审查。

把两篇文章放在一起看，Meta 的架构在流程上落实了验证。以下对应关系是我的解读，Meta 原文没有引用 Osmani：

  • 第 2 步查重、第 5 步可靠性检查由代码执行，不依赖大模型主动遵守。
  • 模板中的「校验」「测试」「监控」是固定阶段，执行顺序由确定性流程安排，无需模型决定是否执行。
  • 专门的校验 Agent 在自己的上下文中工作，接近 Osmani 所说的「独立上下文评审」。
  • Meta 计划用生产数据自动发现失败模式，并提出知识文件的改进建议，但原文强调始终由人审核把关。这与 Osmani 所说的「把每次出错写成规则，让品味复利」思路相通。

Osmani 讨论如何建立验证循环，Meta 则展示了如何通过架构保证这些验证步骤得到执行。

七、什么时候不该用（我的判断）

以下几条是我的判断，不是 Meta 原文的内容。

  • 流程尚未固定时，不宜急着拆分。 模板的前提是步骤和顺序已经明确。对于探索期的产品，一个 Agent 配合少量工具，迭代会更快。
  • 低负载时，先实测编排开销。 西奈山的论文也提到，编排存在固定开销，包括编排器和 worker 的调用、重复的提示词等。批量较小时，有些模型的总 token 用量和延迟反而更高。任务量不大时，应先在自己的场景中测试。
  • 开放式、需要全局视野的任务不适合。 对跨模块的大规模重构来说，「没有任何 Agent 看到全貌」可能成为缺点，需要额外设计专家之间的交接方式。
  • 维护成本会从提示词转移到模板和知识文件。 25 个以上的知识文件同样需要有人维护并进行版本管理。
  • 效果数字有适用边界。 这篇工程文章未提供幻觉率、评估集、样本量等细节，「三分之二无需大改」也没有对比基线，目前尚未看到独立复现。不能把这些数字当成采用后必然达到的结果。

八、小团队可以怎样开始

前四组主要整理自 Meta 和 Osmani 的文章；标有「我的补充」的内容和最后一组是我的建议。

架构

  • 先明确每个组件负责的是路由决策（确定性），还是推理任务（概率性），将两类职责分开。
  • 编排器不包含领域知识；如果它开始作出领域判断，就需要检查是否承担了过多职责。
  • 路由优先使用关键词、意图分类、字段收集等确定性手段。（我的补充：如果确实需要模型分类，也只让它输出一个枚举值。）

专家

  • 每个专家沿用相同结构：知识来源、必需输入、执行步骤、常见错误处理。
  • 一个专家只加载自己领域的知识，避免为图方便而加入所有文档。
  • 用文件管理知识，运行时按需加载，使更新可以直接生效。（我的补充：放进 git 做版本管理。）

扩展

  • 面对新需求，先检查能否通过重新安排现有专家的顺序来完成。
  • 如果专家无法在多个流程中复用，说明它与某个场景绑定得过紧。

验证

  • 分派前用确定性流程检查重复项、必填字段、权限和「需要人审」的标记。
  • 在模板中固定校验或测试阶段，不把是否验证交给模型决定。
  • 验证循环要快、结果要确定，失败信息要简短具体。
  • 将每次错误整理成知识文件中的规则或一个测试，由人审核后合入。

起步顺序（我的建议）

  • 先选一个使用最频繁、步骤最固定的流程，拆出 2–3 个专家，跑通后再扩展，不必一开始就做 14 个。

以 AI 工作区类产品为例，使用频繁、步骤固定的流程适合先做成模板，开放式对话则可以继续交给通用 Agent。两种模式可以并存。这只是一般性的举例，不代表任何具体产品已经采用这套架构。

让每一层承担合适的职责

Meta 的一个判断是：在他们的 Agent 系统中，最重要的组件恰恰是承担具体工作最少的那个。

这段经验提醒我们，不必把所有改进都寄托在让中间的「大脑」更聪明上。中间层可以尽量简单、确定，把需要推理的工作交给边界清晰、上下文独立、结果可验证的专家。薄编排器负责分工，专家积累领域知识，验证则成为流程中固定的一部分。
